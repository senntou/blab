# design.alab.md レビュー（ALab 時代）

**これは ALab 時代の設計レビューである。** 対象は当時の `design.md`（現在の
[design.alab.md](design.alab.md)）で、blab の設計は [design.md](design.md) を参照。
ここでの指摘はすべて反映済みで、blab もその決定（UTC 固定・ULID 末尾 4 文字の短 ID・
heartbeat のデーモンスレッド・params のドット禁止など）をそのまま引き継いでいる。

対象: `docs/design.md`(2026-08-14 時点)。`what.md` の要件との整合も確認した。

> **2026-08-14 追記**: 本レビューの指摘はすべて design.md に反映済み。決定内容 — TZ は UTC 固定、symlink モードは当面廃止(非目標へ)、heartbeat はデーモンスレッド(15 秒毎更新 / stale 閾値 60 秒)、短 ID は ULID 末尾 4 文字、group に status 追加、params のドット禁止、log_summary は shallow merge、step 省略時は自動採番、ほか軽微な指摘も反映。

## 総評

全体として非常に良い設計。「ファイルシステムが唯一のインターフェース」「記録層と閲覧層が互いを知らない」という軸が最後まで一貫しており、what.md の要件(階層構造 = ディレクトリ構造、UI と保存の独立、CV 集計、比較ビュー、parquet)もすべてカバーされている。実装フェーズの切り方も M1〜M3 で最小構成が成立する健全な順序になっている。

以下は実装前に仕様として詰めておくべき点。**要対応**は実装に入る前に決めるべきもの、**軽微**は M1 中に決めれば足りるもの。

## 要対応

### 1. 短 ID と ULID の関係が未定義(§2.1 / §2.2)

ディレクトリ名は `短ID 4桁`(例 `a1b2`)、`meta.json` の `id` は ULID と、識別子が 2 つある。短 ID を ULID の末尾から導出するのか独立乱数なのかを仕様に書くべき。また「同名連投でも衝突しない」とあるが、同一秒・同名・4 桁 hex なら 1/65536 で衝突しうる。作成時に `os.mkdir` の失敗(既存)を検出して短 ID を引き直す、と一行明記しておくと閉じる。

### 2. ディレクトリ名のタイムスタンプのタイムゾーン(§2.1)

`created_at` は `+09:00` 付きだが、ディレクトリ名の `YYYYMMDD-HHMMSS` はどのタイムゾーンか未定義。「rsync でそのまま持ち運べる」を売りにする以上、TZ の異なるマシンで作った run を混ぜると名前の時系列順が崩れる。UTC 固定を推奨(見た目のローカル時刻は UI 側で `created_at` から出せる)。

### 3. Group に status がない(§2.2)

run は `running | finished | failed | killed` を持つが、group の meta には `finished_at` しかない。CV の途中で group コンテキストマネージャが例外脱出した場合の扱い(summary を書くのか、`failed` を記録するのか)が決まっていない。run と同じ status を持たせるのが素直。あわせて group summary に `count` だけでなく `n_failed`(または集計対象外の run 数)を出すと、「fold が 1 つ落ちて 4 fold の平均になっている」ことに気づける。§4 の集計仕様は fold 欠落を静かに許す設計なので、これは実害のあるギャップ。

### 4. heartbeat の更新機構が未定義(§2.2 / §3)

`heartbeat_at` を「定期更新」とあるが、誰がいつ更新するかがない。`log()` 契機だと epoch 間の長い評価中に stale 誤検出するし、バックグラウンドスレッドなら記録層の「決して学習を落とさない」との整合(スレッド例外の扱い、fork との相性)を書く必要がある。更新間隔と UI 側の stale 閾値(例: 更新 30 秒毎 / 閾値 3 倍)もセットで決めるべき。heartbeat 毎に `meta.json` 全体を `os.replace` する設計なので、頻度が高いと mtime ベースの UI キャッシュ(§5.1)が毎回 meta を読み直す点も意識しておく。

### 5. `mode="symlink"` と `/files` のパス脱出禁止が矛盾しうる(§3.1 / §5.1)

`log_artifact(mode="symlink")` はルート外を指す symlink を artifacts/ に作る。一方 `/files/{path}` は「ルート外へのパス脱出を禁止」。`..` の拒否だけでは symlink 経由の脱出は防げないので、`realpath` 解決後にルート配下か検証するのか、symlink は自分で作ったものだから許容するのかを決めて明記する必要がある。禁止に倒すなら symlink モードのアーティファクトは UI で見えなくなるので、その旨も仕様に書く。

### 6. params のフラット化の衝突と非スカラ値(§2.2 / §5.2)

`params.json` は任意ネストを許可し UI でドット区切りにフラット化するが、(a) `{"a.b": 1}` と `{"a": {"b": 1}}` が同じ列名 `a.b` に潰れる、(b) リストなど非スカラの葉をテーブル列にどう出すか、が未定義。(a) はキーにドットを禁止するのが簡単。(b) は JSON 文字列化して表示、で十分。

## 軽微

- **`log_summary` の複数回呼び出し**(§3.1): マージか置換か未定義。マージ(shallow merge)を推奨。
- **`_time` の単位**(§2.2): 例が `1786...` で unix 秒らしいが、秒か ミリ秒かを明記する。
- **ネストした group の集計**(§4): 「配下(再帰的に)の run を集める」とあるが、内側 group 自身の summary.json は無視して葉の run だけ集める、と明示した方が二重集計の疑義がなくなる。
- **ルート探索の挙動**(§3.1): 「cwd から上に `alab.json` を探す」は、別プロジェクトのサブディレクトリで実行したとき意図しないルートに書く事故がありうる。探索でヒットしたパスを init 時に一度ログ出力すると安全。
- **索引の削除検出**(§5.1): mtime 差分で「変わったもの」を読み直す設計だが、`alab rm` された run の索引からの除去(消えたディレクトリの検出)も一行書いておく。また新規 run の検出はポーリング毎のフルウォークになるので、run 数が数千を超えたときの走査コストは §10 の未決事項(巨大 metrics)と同様に実測対象に入れておくとよい。
- **`max_points` の間引き方法**(§5.1): 等間隔ストライドか LTTB か。折れ線の見た目に効くので、最初は等間隔で始めて明記だけしておく。

## 未決事項(§10)への意見

- **ULID 自前実装**: 標準ライブラリのみで問題なく書ける(`time` + `secrets`)。妥当。
- **step 省略時の挙動**: 自動採番(内部カウンタのインクリメント)を推奨。「直前 step の上書き」は JSONL 追記オンリーの原則と噛み合わない(同一 step の行が複数できて読み手側でマージが要る)。
- **アーティファクト既定モード**: コピー既定で良い。symlink は §「要対応 5」を解決してから。

## 良い点(維持してほしい設計判断)

- 記録層は標準ライブラリのみ、UI は extras という依存の切り分け。
- `os.replace` + 「JSONL の不完全末尾行は読み手が捨てる」という、ロックなしで成立する原子性の設計。
- parquet を「正のデータ」ではなく派生キャッシュに位置づけ、SQL を当面スコープ外にした判断。
- 非目標(§9)が明文化されていること。特に「UI からの書き込みをしない」は 2 層独立の原則を守る良い制約。
